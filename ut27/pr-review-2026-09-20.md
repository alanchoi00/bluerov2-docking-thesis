## 1. Must fix before the abstract upload (28 Sep) and before merging thesis #9 and #10

### Fine controller feedforward gain is 1.0, not 0.6

`ff_velocity_gain: 0.6` exists only in `coarse_pbvs.yaml` and is applied only by `coarse_approach_node.py` (times a distance ramp). `fine_align_node.py` passes the dock velocity straight through ("Fine passes full authority"), scaled by 0.5 only while the filter is DEGRADED, and clamped at 0.25 m/s. The fine node never had a gain (history of `ff_velocity_gain` is one commit, #59, coarse only).

Empirical check (`ffgain.py`, regression of the recorded lateral command on the estimated dock velocity and the lateral error, clamped sweep, phase 0):

| Period | COARSE ff coefficient | FINE ff coefficient | FINE R2 |
| --- | --- | --- | --- |
| 20 s | 0.66 | 1.13 | 0.69 |
| 16 s | 0.32 | 0.85 | 0.42 |
| 12 s | 0.34 | 0.84 | 0.46 |
| 10 s | 0.14 | 0.64 | 0.44 |
| 8 s | 0.29 | 0.76 | 0.74 |
| 6 s | 0.32 | 0.86 | 0.81 |

Both failures (8 s blackout, 6 s never advances) happen in FINE. So the chain "0.6 x 2.7 = 1.6, which is the measured over-swing" is the coarse gain applied to fine-phase failures. In FINE the feedforward alone drives about 2.7 times the dock velocity and the position feedback (kp 0.8, kd 0.3) pulls it back to the measured 1.6 to 1.7. The mechanism is unchanged and stronger, but these sentences are wrong:

- Section III (thesis #9): "Both controllers accept a dock-velocity feedforward ... scaled by a gain of 0.6". Correct: coarse 0.6 with a ramp, fine 1.0.
- Section IV (thesis #9): "the lateral command in the tracking windows is 90 to 100 percent feedforward" and "0.6 x 2.7 ~ 1.6 ... which is the measured over-swing". In FINE the feedforward exceeds the command and feedback opposes about a third of it.
- Section IV loop interpretation: "with K_ff g between 1.3 and 3" should be K_ff g = 1.6 (coarse) and 2.7 (fine).
- `t1-leak-diagnosis.md` Sections 2 and 11 (the "of which 0.049 is feedforward at gain 0.6" rows come from the `ff_gain=0.6` default in `loop.py`), `abstract_v2.tex`, and the #67 issue body carry the same arithmetic.

Also note for the T5 design: the velocity-closed feedforward removes this per-phase gain inconsistency, which is a further argument for it.

## 2. Code PRs: findings

### #79 sweep runner (three real defects)

1. **Crashed trials are skipped as done on resume.** `run_docking_sweep.sh:51` marks a cell done if any `bags/<label>_*` directory exists. `ros2 bag record` creates the directory at start, so a trial killed by a thermal crash is skipped forever with a routine SKIP line. Fix: require `metadata.yaml` in the bag (the per-trial script already reindexes when it is missing) or an outcome row in the CSV.
2. **Arm C silently runs as arm B.** `run_docking_trial_auto.sh:39` passes `feedforward_mode:=velocity_loop stale_velocity_decay_s:=1.0`, which no launch file declares; `ros2 launch` ignores unknown arguments. An unattended sweep with C in ARMS would produce bags labelled C that are really B. Fix: exit 2 on arm C until the T5 launch arguments exist, or drop C from the default arm list with a loud comment.
3. **No trap in the sweep script.** Killing the sweep by PID (the realistic unattended stop) leaves the running trial's whole tree (gz, ardusub, recorder) orphaned. Fix: trap INT TERM and forward to the child's process group, or run the child under setsid and kill its group.

Also both scripts use `set -uo pipefail`; every variable is guarded so it does not bite today, but the project rule is no `-u` in scripts that may source ROS setup files.

### #78 step-test recorder (one defect)

`scripts/plantid/record_step_tests.sh` backgrounds the recorder (`REC=$!`) and stops it only on the success path; there is no trap, so Ctrl-C mid-run orphans `ros2 bag record`. Fix: `trap 'kill -TERM $REC 2>/dev/null' EXIT` right after `REC=$!`.

### #75 offline replay (test gap)

The 0.3 to 0.8 cm RMS reproduction claim and the "decay only after the hold time" gating are only demonstrated in the PR description. Add a fixture test for both. #76 and #77 import `replay()`, so a later drift would be silent.

### #73, #74, #76, #77, #80, #81, #82: no defects found

Checked specifically: metrics constants and outcome logic against `rescore_contacts.py` (exact match); mount transform and quaternion convention (unit tested); slerp duplicate stamps (guarded and tested); Gauss-Markov discretisation (per-step std sigma_b sqrt(1 - rho^2), tested); relative filter B sign (tested against a moving vehicle); chi-square gate on the pre-update innovation covariance; oracle timestamps come from the Gazebo pose header (sim time), oracle frame and QoS match both control nodes; injector RELIABLE and gated off when the level is none; #82 leaves only the TF grace on wall clock, zero clock before /clock is safe, the dt clamp does not touch the stale ages, backward jumps skip predict.

Low-confidence notes (no action needed): `load_trial` checks raw `/tf` message count rather than the map to base_link count, so a bag without the relay fails with a generic error; `estimation()` interpolates the health enum linearly between 30 Hz samples (one-tick effect); `overswing()` and `trial_metrics()` have no unit tests; `plantid.py` has no tests (superseded by the step tests).
